    \section{Einleitung}

    \subsection{Überblick}
    Die Entwicklung moderner Softwaresysteme erfordert Lösungen, die sowohl flexibel als auch wartbar und erweiterbar
    sind. Entwurfsmuster (Design Patterns) stellen hierfür bewährte Konzepte bereit, indem sie wiederkehrende Probleme
    der objektorientierten Softwareentwicklung auf standardisierte Weise lösen. Sie bieten keine fertigen
    Implementierungen, sondern beschreiben allgemeine Lösungsansätze, die abhängig vom jeweiligen Anwendungsfall
    angepasst werden können.

    Das Command Pattern gehört zu den verhaltensorientierten Entwurfsmustern und dient dazu, Anweisungen oder
    Operationen als eigenständige Objekte zu kapseln. Durch diese Kapselung werden aufrufende und ausführende
    Komponenten voneinander entkoppelt, wodurch sich Befehle flexibel verwalten, weitergeben oder zu einem späteren
    Zeitpunkt ausführen lassen. Aufgrund dieser Eigenschaften findet das Muster in verschiedenen Bereichen der
    Softwareentwicklung Anwendung, etwa bei grafischen Benutzeroberflächen, Undo/Redo-Funktionalität oder der
    Verarbeitung von Befehlswarteschlangen.\footnote{\cite{schiele-command}}

    Ziel dieser Hausarbeit ist es, das Command Pattern vorzustellen und dessen grundlegendes Konzept zu erläutern.
    Hierzu werden zunächst die Funktionsweise sowie die beteiligten Komponenten des Entwurfsmusters beschrieben.
    Anschließend werden typische Einsatzgebiete vorgestellt und anhand einer beispielhaften Implementierung die
    praktische Anwendung des Musters verdeutlicht. Ergänzend werden UML-Diagramme verwendet, um den strukturellen
    Aufbau sowie das Zusammenspiel der beteiligten Klassen anschaulich darzustellen.\footnote{\cite{gamma1995design}}

    \subsection{Problemstellung}
    In vielen Anwendungen werden Benutzeraktionen direkt mit der auszuführenden Programmlogik verknüpft.
    Ein typisches Beispiel ist eine grafische Benutzeroberfläche (UI), in der verschiedene Buttons bestimmte Funktionen
    auslösen. So kann beispielsweise ein Button zum Speichern eines Dokuments, ein weiterer zum Drucken und ein dritter
    zum Löschen einer Datei dienen. Wird die jeweilige Funktion direkt im Code des Buttons implementiert, entsteht eine
    enge Kopplung zwischen der Benutzeroberfläche und der eigentlichen Geschäftslogik.

    Diese enge Abhängigkeit führt zu mehreren Problemen. Zum einen wird die Wiederverwendbarkeit der Funktionalität
    eingeschränkt, da dieselbe Aktion beispielsweise nicht ohne Weiteres über Tastenkombinationen, Menüeinträge oder
    andere Eingabemethoden ausgelöst werden kann. Zum anderen erschwert die direkte Verknüpfung die Wartung und
    Erweiterung der Software. Jede Änderung an einer Funktion erfordert häufig auch Anpassungen an den entsprechenden
    UI-Komponenten. Mit zunehmender Anzahl an Buttons und Funktionen wird der Quellcode dadurch unübersichtlicher und
    schwieriger zu pflegen.

    Ein weiteres Problem ergibt sich, wenn zusätzliche Anforderungen wie eine Undo-/Redo-Funktion, das Protokollieren
    ausgeführter Aktionen oder die zeitversetzte Ausführung von Befehlen umgesetzt werden sollen. Sind die Aktionen
    fest in den UI-Elementen implementiert, lassen sich solche Erweiterungen nur mit erheblichem Aufwand realisieren.

    Zur Veranschaulichung kann eine Textverarbeitungsanwendung betrachtet werden. Dort besitzt die Benutzeroberfläche
    unter anderem die Buttons \textit{Speichern}, \textit{Drucken} und \textit{Rückgängig}. Jeder Button soll eine
    bestimmte Aktion auslösen, unabhängig davon, ob diese über einen Mausklick, einen Menüeintrag oder eine
    Tastenkombination aktiviert wird. Um diese Flexibilität zu erreichen, muss die Benutzeroberfläche von der
    eigentlichen Ausführung der Aktionen entkoppelt werden. Genau an dieser Stelle setzt das Command Pattern an, indem
    jede Benutzeraktion als eigenständiges Befehlsobjekt gekapselt wird. Die UI kennt lediglich das jeweilige Kommando
    und muss keine Details über dessen konkrete Implementierung oder Ausführung besitzen.


    \section{Klassifizierung anhand des Vier-Punkte Schemas}

    \subsection{Name}
    Das Entwurfsmuster trägt den Namen Command-Pattern. Im deutschsprachigen Raum wird es als Kommando-Muster bezeichnet.
    Es gehört zur Kategorie der Verhaltensmuster (Behavioral Patterns).

    \subsection{Lösung}

    \begin{figure}[h!]
        \centering
        \includegraphics[width=15cm]{img/uml-class-diagramm-command-pattern}
        \caption{UML Klassendiagramm: Command Pattern}
        \label{fig:uml_command_pattern}
    \end{figure}



    Das Command-Pattern löst die enge Kopplung zwischen Sender und Empfänger durch eine objektorientierte Kapselung.
    Es transformiert eine Anfrage oder Operation in ein eigenständiges Objekt, das alle für die Ausführung notwendigen Informationen
    in sich speichert. Dadurch wird der direkte Methodenaufruf abstrahiert. Die Architektur nutzt hierfür ein gemeinsames Interface,
    welches eine einzige Methode namens \texttt{execute()} vorschreibt. Der Sender der Anfrage interagiert ab
    sofort ausschließlich mit diesem Interface, wodurch er die konkrete Implementierung der dahinterliegenden Logik nicht mehr kennen muss.

    Die Funktionsweise des Musters basiert auf dem strukturierten Zusammenspiel von vier zentralen Akteuren.

    \begin{itemize}
        \item \textbf{Klient (Client):} Der Klient steuert den initialen Ablauf. Er erzeugt das konkrete Kommando-Objekt
        und injiziert dabei den passenden Empfänger. Anschließend weist er das fertig konfigurierte Kommando dem Aufrufer zu.
        \item \textbf{Aufrufer (Invoker):} Der Aufrufer fungiert als reiner Auslöser der Anfrage und hält eine Referenz auf
        das Command-Interface. Da er die konkrete Implementierung nicht kennt, ist ihm die genaue Funktion des Kommandos verborgen.
        Zu einem festgelegten Zeitpunkt ruft er lediglich die \texttt{execute()}-Methode des Kommandos auf.
        \item \textbf{Kommando (Command):} Das Kommando bildet das Bindeglied der Architektur und implementiert das gemeinsame
        Interface. Es kapselt die Anfrage und delegiert in seiner \texttt{execute()}-Methode die eigentliche Arbeit an den Empfänger.
        Das Kommando führt die komplexe Logik folglich fast nie selbst aus.
        \item \textbf{Empfänger (Receiver):} Der Empfänger enthält die eigentliche Geschäftslogik und führt die tatsächlichen Berechnungen
        oder Zustandsänderungen durch. Er kommuniziert niemals direkt mit dem Aufrufer, sondern erhält seine Arbeitsaufträge ausschließlich über das zwischengeschaltete Kommando-Objekt.
    \end{itemize}

    Durch diese klare Aufteilung wird eine vollständige Entkopplung der Komponenten erreicht: Der Aufrufer erteilt lediglich den Befehl, das Kommando transportiert sowie übersetzt ihn, und der Empfänger führt ihn schließlich aus. Nachträgliche Änderungen an der Geschäftslogik des Empfängers bleiben somit ohne jegliche Auswirkung auf den Aufrufer.

    \subsection{Konsequenzen}
    Dieses Vorgehen bringt deutliche Vor- und Nachteile mit sich. Der größte Vorteil ist die starke Entkopplung der Komponenten.
    Absender und Empfänger sind völlig unabhängig. Neue Kommandos lassen sich jederzeit hinzufügen. Der bestehende Code bleibt
    dabei unberührt. Der primäre Nachteil ist die steigende Komplexität. Für jeden neuen Befehl muss eine eigene Klasse programmiert
    werden. Die reine Anzahl der Klassen wächst im System dadurch stark an. Ein weiterer großer Vorteil ist jedoch, dass diese
    Struktur mächtige funktionale Erweiterungen ermöglicht.

    \section{Erweiterungsmöglichkeiten}

    Das Command-Pattern bietet durch seine entkoppelte Struktur eine ideale Basis für fortgeschrittene Architekturen.

    \subsection{Undo- und Redo-Mechanismen}

    \begin{figure}[H]
        \centering
        \includegraphics[width=15cm]{img/undo-redo-class-diagramm}
        \caption{UML Klassendiagramm: Command Pattern Erweiterung mit Undo/Redo}
        \label{fig:uml_command_pattern_undo}
    \end{figure}

    Aktionen können leicht rückgängig gemacht werden. Dafür wird das Interface um eine \texttt{undo()}-Methode ergänzt.
    Das Kommando speichert intern den Zustand vor der Ausführung. Bei einem Undo-Aufruf stellt es diesen Ursprungszustand
    wieder her. Redo-Operationen können das Kommando danach einfach erneut ausführen. Um einen komplexen Zustand wiederherzustellen,
    lässt sich das Command-Pattern mit dem Memento-Pattern\footnote{Weiterführende Info: \href{https://refactoring.guru/design-patterns/memento}{Memento-Pattern (letzter Aufruf: 19.07.2026)}} kombinieren.

    \subsection{Makros (Befehlsketten)}
    \begin{figure}[h!]
        \centering
        \includegraphics[width=15cm]{img/makro-class-diagramm}
        \caption{UML Klassendiagramm: Command Pattern Erweiterung mit Makros}
        \label{fig:uml_command_pattern_makro}
    \end{figure}

    Mehrere Einzelkommandos können zu sogenannten Makros gebündelt werden. Dies geschieht über ein übergeordnetes Makro-Kommando.
    Es implementiert ebenfalls das Standard-Interface. In seiner \texttt{execute()}-Methode arbeitet es nacheinander eine Liste
    von Teilkommandos ab.

    \subsection{Warteschlangen und Logging}
    \begin{figure}[h!]
        \centering
        \includegraphics[width=15cm]{img/logging-queuing-class-diagramm}
        \caption{UML Klassendiagramm: Command Pattern Erweiterung durch Queue und Logging}
        \label{fig:uml_command_pattern_queue}
    \end{figure}

    Befehle lassen sich in einer Warteschlange (Queue) speichern. Dadurch können sie asynchron zu einem späteren Zeitpunkt
    ausgeführt werden, was bei der Verwaltung von Thread-Pools von großen Vorteil ist. Zudem ermöglicht die reine Objektform ein einfaches Logging.
    Jeder ausgeführte Befehl kann in einer Datei gespeichert oder in der Konsole ausgegeben werden. Bei einem Systemabsturz lassen sich
    die Aktionen aus dem Log wiederherstellen.

    \section{Praxisbeispiel in Java}

    Zur Veranschaulichung wird das Command-Pattern nachfolgend anhand eines bewusst schlank gehaltenen,
    aber vollständigen Beispiels in Java umgesetzt. Als Szenario dient eine Fernbedienung, die eine Lampe
    ein- und ausschaltet. Trotz seiner Einfachheit deckt das Beispiel alle vier zuvor beschriebenen Rollen
    des Musters ab (vgl. Abbildung~\ref{fig:uml_command_pattern}) und lässt sich unmittelbar auf diese abbilden:

    \begin{itemize}
        \item \textbf{Kommando (Command):} das Interface \texttt{Command},
        \item \textbf{Empfänger (Receiver):} die Klasse \texttt{Light},
        \item \textbf{Konkrete Kommandos:} \texttt{LightOnCommand} und \texttt{LightOffCommand},
        \item \textbf{Aufrufer (Invoker):} die Klasse \texttt{RemoteControl},
        \item \textbf{Klient (Client):} die Klasse \texttt{Main}.
    \end{itemize}

    Den Ausgangspunkt bildet das gemeinsame Interface \texttt{Command}. Es schreibt mit \texttt{execute()}
    genau eine Methode vor und stellt damit die einheitliche Schnittstelle dar, über die sämtliche Befehle
    ausgelöst werden.

    \begin{lstlisting}[caption={Das Kommando-Interface \texttt{Command}}, label={lst:command}]
// Kommando-Interface
public interface Command {
    void execute();
}
    \end{lstlisting}

    Der Empfänger enthält die eigentliche Geschäftslogik. Im Beispiel ist dies die Klasse \texttt{Light},
    welche die konkreten Operationen zum Ein- und Ausschalten bereitstellt. Sie besitzt keinerlei Kenntnis
    vom Command-Pattern und könnte unverändert auch ohne dieses verwendet werden.

    \begin{lstlisting}[caption={Der Empfänger \texttt{Light}}, label={lst:light}]
// Empfänger - führt die eigentliche Arbeit aus
public class Light {
    public void on()  { System.out.println("Light is ON"); }
    public void off() { System.out.println("Light is OFF"); }
}
    \end{lstlisting}

    Die konkreten Kommandos kapseln jeweils eine Anfrage an den Empfänger. Sie implementieren das Interface
    \texttt{Command} und halten eine Referenz auf das \texttt{Light}-Objekt. In der \texttt{execute()}-Methode
    delegieren sie die Arbeit an den Empfänger, anstatt die Logik selbst auszuführen.

    \begin{lstlisting}[caption={Die konkreten Kommandos \texttt{LightOnCommand} und \texttt{LightOffCommand}}, label={lst:concrete}]
// Konkretes Kommando - kapselt "Licht einschalten" als Objekt
public class LightOnCommand implements Command {
    private final Light light;

    public LightOnCommand(Light light) { this.light = light; }

    public void execute() { light.on(); }
}

// Konkretes Kommando - kapselt "Licht ausschalten" als Objekt
public class LightOffCommand implements Command {
    private final Light light;

    public LightOffCommand(Light light) { this.light = light; }

    public void execute() { light.off(); }
}
    \end{lstlisting}

    Der Aufrufer löst Befehle aus, ohne deren konkrete Implementierung zu kennen. Die Klasse
    \texttt{RemoteControl} hält lediglich eine Referenz auf das \texttt{Command}-Interface und ruft bei
    einem Tastendruck dessen \texttt{execute()}-Methode auf. Welches Kommando dabei ausgeführt wird und was
    dieses bewirkt, bleibt dem Aufrufer verborgen.

    \begin{lstlisting}[caption={Der Aufrufer \texttt{RemoteControl}}, label={lst:invoker}]
// Aufrufer - löst Kommandos aus, ohne ihre Wirkung zu kennen
public class RemoteControl {
    private Command command;

    public void setCommand(Command c) { command = c; }
    public void pressButton() { command.execute(); }
}
    \end{lstlisting}

    Der Klient verknüpft schließlich die Komponenten miteinander. Er erzeugt den Empfänger, instanziiert
    die konkreten Kommandos mit diesem Empfänger und übergibt sie dem Aufrufer. Anschließend genügt ein
    Aufruf von \texttt{pressButton()}, um den jeweiligen Befehl auszuführen.

    \begin{lstlisting}[caption={Der Klient \texttt{Main}}, label={lst:client}]
public class Main {
    public static void main(String[] args) {
        Light light = new Light();
        RemoteControl remote = new RemoteControl();

        remote.setCommand(new LightOnCommand(light));
        remote.pressButton();

        remote.setCommand(new LightOffCommand(light));
        remote.pressButton();
    }
}
    \end{lstlisting}

    Die Ausführung des Programms erzeugt die folgende Ausgabe:

    \begin{lstlisting}[language={}, caption={Konsolenausgabe des Beispiels}, label={lst:output}]
Light is ON
Light is OFF
    \end{lstlisting}

    Das Beispiel verdeutlicht die zentrale Eigenschaft des Musters: Die Klasse \texttt{RemoteControl}
    besitzt keinerlei Wissen über die Klasse \texttt{Light}. Der Aufrufer kommuniziert ausschließlich mit
    dem \texttt{Command}-Interface, während die eigentliche Logik im Empfänger gekapselt bleibt. Soll die
    Fernbedienung künftig ein anderes Gerät steuern, muss lediglich ein neues konkretes Kommando ergänzt
    werden. Weder der Aufrufer noch der bestehende Code müssen dafür verändert werden, was die im vorherigen
    Abschnitt beschriebene Entkopplung praktisch belegt.
